# 研究范围与确认结论

本轮研究目标不是重复创建临时游客账号，而是定位最终游客弹窗点击后的真实分支，尽可能在**本人控制且能保留 userdata 的 Android** 上完成一次正常流程，确认：

`ConfirmGestAccountSecond → decision thunk → DecisionGestAccount → AtuhRegisterUser → SerializeRequestParameter → CallAfterResponse → Token/Login → SetBasic → basic.utid`。

静态链路不能代替服务端响应，也不能把“方法入口命中”当成“用户注册完成”。

## 1. 原版 4.1.0 的字节证据

原版 APK SHA-256：
`8dee598028cd70441f645c8fff96b093b76778d625cdf07c60109eced50ffac1`

原版 ARM64 `libil2cpp.so` SHA-256：
`80bfbc3d480bf3c91297d65a441a37e40260b70fd8b0ddc8da70c34f0870b6fe`

使用 `ci/home41_guest_native_static.py` 先核对 APK / SO 哈希，再按 AArch64 ELF64 的可执行 PT_LOAD 映射 RVA，核查分支指令。已由 [Actions #42570544265](https://github.com/969981/Home_Android/actions/runs/42570544265) 在原始字节上成功验证八条分支和回调窗口。

| 原版指令 RVA | 指令 | 目标 | 证据用途 |
| --- | --- | --- | --- |
| `0x1DE53DC` | BL | `0x1DEB3C0` | 第二确认原生方法的直接被调位置；身份未完全闭合 |
| `0x1DEB4A4` | B | `0x1DE5508` | 正向跳板尾调用 `DecisionGestAccount` |
| `0x1DEB58C` | B | `0x1DE5698` | 拒绝跳板尾调用 `DenialGestAccount` |
| `0x1DE5690` | B | `0x1D2F8DC` | `DecisionGestAccount` 尾调用 `ApiManagerLogin.AtuhRegisterUser` |
| `0x1DE64D0` | B | `0x1DE1C10` | 回调 `b__84_6` 转入 `GoToPhase` |
| `0x1DE64E4` | B | `0x1DE1C10` | 回调 `b__84_7` 转入 `GoToPhase` |
| `0x1DE64F8` | B | `0x1DE1C10` | 回调 `b__84_8` 转入 `GoToPhase` |
| `0x1DE65C8` | B | `0x1DE1C10` | 回调 `b__84_10` 转入 `GoToPhase` |

注意：`0x1DEB4A4 → DecisionGestAccount` 和 `DecisionGestAccount → AtuhRegisterUser` 静态指令目标已验证，但**真正的 UI 按钮是否选中了正向 Closure / 委托**仍须运行时证明。不同线程事件的时间先后不能自动视为同一个注册事务的因果链。

另外，曾标为未知 `post_guest` 候选的 `0x1DE1098` 和 `0x1DE16F4`，实际是 `_AddWarningPart` 和 `_AddPadder` UI 辅助函数，不能当作注册回调。真正头像及序章的具名入口包括 `SelectTrainerIcon 0x1DE48F8`、`PlayPrologue 0x1DE45E8`、`PlayPrologue2 0x1DE4CF4`、`FirstBootProloguePokemonPanel.OnTapPokemon 0x1C7F0F4`。

## 2. 最新 Frida 覆盖率防误判

`ci/home41_arm64_auth_timeline.js` 现在在原生 Hook 安装时记录**真实的 attach 成功/失败**，并由 `ci/home41_arm64_auth_timeline.py` 严格过滤成固定布尔值，见 `guest_chain_critical_hook_coverage`：

- `confirm_second`：第二次游客确认
- `positive_thunk` / `negative_thunk`：正向/拒绝跳板
- `decision_controller` / `denial_controller`：原生决定/拒绝方法
- `go_to_phase`：请求切换阶段
- `register_manager`：`AtuhRegisterUser`
- `register_serializer` / `register_response`：注册 DTO 入口/响应回调

报告有 `guest_chain_diagnosis`：`classification` 表示同一观察窗口已经看见的最远节点（或关键异常），`observed_checkpoints` 罗列已见入口，`missing_or_unverified_critical_hooks` 列出安装失败或未知的 Hook。**Hook 未安装时，计数为 0 不能解释为游戏函数没有调用。**

典型状态及进一步动作：

| `classification` | 能证明什么 | 下一道检查 |
| --- | --- | --- |
| `second_confirmation_not_observed` | 这次未观察到 Second | 核对是否提前附加，以及 Second Hook 是否安装 |
| `second_seen_no_followup_in_observation_window` | 第二确认已见，后继未见 | 核对正/负跳板和注册 Hook 覆盖，再看原版 UI |
| `positive_thunk_seen_decision_controller_not_observed` | 见到正向跳板入口 | 核对 Decision 方法与对象身份 |
| `decision_controller_seen_register_manager_not_observed` | Decision 方法进入 | 核对原始 B 尾跳转实际执行、是否发生提前退出 |
| `register_manager_seen_serializer_not_observed` | 注册管理器进入 | 核对原生请求路径、序列化入口 |
| `registration_serializer_seen_http_send_not_proven` | 注册参数序列化进入 | 仍需正常服务端响应，不能称 HTTP 已发送 |
| `registration_response_callback_seen_result_unknown` | 注册响应方法进入 | 需要判断回调成功/失败，继续看 Token/Login |
| `first_basic_seen_ui_six_digit_id_not_verified` | 观察到来自公共 Basic 消费点的资料 | 与 HOME 原版六位 ID 对照、冷启动复查 |
| `first_basic_event_without_verified_common_caller` | Basic 事件来源未验证 | 不允许把它当作已证实资料 |
| `guest_denial_path_observed` / `mixed_guest_decisions_require_instance_correlation` | 拒绝或混杂分支证据 | 核对事件对象身份和真正的 UI 委托绑定 |

`server_registration_confirmed`、`ui_six_digit_id_verified`、`cold_start_account_restored_verified` 仍统一为 false。没有服务器实证不能把测试假事件改成 true。

## 3. Windows 本地持久设备的单次观察

在 `Home_Android` 仓库根目录，先准备原版 `4.1.0` APK、可执行的 `adb`、与已授权 Android 设备匹配的 Frida Server。建议优先原生 ARM64 手机；若选 x86_64+ARM NativeBridge 的个人 AVD，使用 `--realm emulated --remote-frida`，并明确标记仿真环境。

```powershell
git pull origin master
py -3 -m pip install frida
adb devices
$apk = (Get-ChildItem '.\ROMS\4.1.0\*.apk' | Select-Object -First 1).FullName
py -3 ci/home41_arm64_readonly_runner.py preflight --apk "$apk"

# 先在原版 HOME UI 进入最终游客确认之前的页面。
# 只读挂载到现有原生 ARM64 进程，不调用 spawn，不终止 APP。
py -3 ci/home41_arm64_auth_timeline.py `
    --apk "$apk" `
    --realm native `
    --attach-running `
    --timeout 1800 `
    --output ".\local-home41-guest-chain.json"
```

在设备上仅进行已经批准的**一次官方初始化**，已定选择是生日 1999/4/5、Nintendo Account 不关联、官方游客确认，之后在实际验证的原版页面选一个有效头像及小火龙，不自动尝试未知控件坐标。让 Frida 在最终第二确认**之前**就安装完关键 Hook；否则无法补抓之前的事件。

现在会在本地终端即时显示固定格式的原生事件（如 Second、正向跳板、Decision、注册管理器、响应、头像/序章），不会输出原始 UTID、令牌、HTTP 正文或其他账户信息。若界面停住，可在本机按 **Ctrl+C**，脚本会获取最新的固定布尔 Hook 覆盖快照、写出脱敏 JSON 并断开 Frida；不清除 HOME 数据、也不执行账号删除或重复注册。

`--show-local-values` 仅为主动允许的本地交互终端显示完整 UTID 的特殊选项；普通验证无需开启。报告 `local-home41-guest-chain.json` 已由 `.gitignore` 忽略，尽管经过脱敏，仍建议不要公开原版注册后截图。

冷启动同号验收仍使用：

```powershell
py -3 ci/home41_arm64_runtime_acceptance.py `
    --apk "$apk" `
    --target 888888 `
    --timeout 600
```

它会在本地无回显输入实际六位 ID，比较两次经真实公共 Basic 调用点读取的候选，要求 Frida 卸载后仍能正常操作、旧进程确实退出、新 PID 不同，并在冷启动后的官方 UI 上再次确认同一 ID。只有实际设备的 `REAL_DEVICE_THREE_GATES_PASSED` 可宣称冷启动验收通过。
